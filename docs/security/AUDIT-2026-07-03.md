### H-01 — `is_protected` bypass em reset de senha de ADMIN

| Campo | Valor |
|---|---|
| **Rule ID** | EXPRESS-INPUT-001 / OWASP A01:2025 (Broken Access Control) |
| **Severity** | **High** (Risk = High × High — privilege escalation direto) |
| **Location** | `src/modules/users/router.ts:47-52` + `src/modules/users/service.ts:31-46` (+ ausência de checagem em `users/controller.ts`) |
| **Evidence** | O router `POST /api/v1/users/:id/reset-password` é ADMIN-only e chama `service.resetPassword(req.params.id, isolationUserId(req))` sem nunca verificar `targetUser?.is_protected`. Em `users/controller.ts:44-62`, o método `update` (que está em rota irmãos `PUT`) faz a checagem explicitamente:<br/><pre>if (targetUser?.is_protected) {<br/>  if (req.user?.role !== 'ADMIN') throw 403;<br/>  const allowedKeys = ['status'];<br/>  ...<br/>}</pre>e em `delete` (L63-72): `if (targetUser?.is_protected) throw 403 'PROTECTED_ADMIN';`. **O endpoint de reset-password é o único dos três que pula essa proteção.** |
| **Impact** | Um ADMIN comprometido (não-principal) consegue redefinir a senha do ADMIN principal (`is_protected=true`) sem nenhuma validação extra. Resultado: account takeover do privileged account. Combinado com a ausência de 2FA, isso quebra o trilho de proteção do "administrator principal". |
| **Fix recomendado** | Replicar a checagem de `is_protected` em `service.resetPassword` (camada service, não controller) e lançar `AppError(403, 'PROTECTED_ADMIN')` quando `targetUser?.is_protected === true`. Como a proteção é invariante de domínio (não decisão de UI), pertence ao service.<br/><br/>Alternativa consciente: tratar o endpoint como **recovery path intencional** e documentar explicitamente no SECURITY.md. Sub-spec 3 decide o caminho; recomendação padrão = replicar a checagem + adicionar 2FA de ADMIN para reset entre pares. |
| **Mitigation (transitória até o fix)** | Limitar o endpoint por IP (`userPasswordResetLimiter` já existe, 5/15min); adicionar log de auditoria de alto risco quando `targetUser.is_protected === true`; revisar diariamente via audit log. |
| **Sub-spec destino** | **3 (correções)** — guardrail de acesso, requer decisão de produto (recovery path vs hard block).<br>**2 (suite)** — adicionar regressão e2e Playwright que tenta resetar ADMIN `is_protected=true` com credencial de ADMIN não-principal e espera 403. |

### M-01 — Documentação stale (Supply Chain): deps com caret contradizem SECURITY.md

| Campo | Valor |
|---|---|
| **Rule ID** | A06:2025 (Software Supply Chain) — drift entre política e package-lock |
| **Severity** | **Medium** (Risk = Medium × Medium — drift de política + higiene) |
| **Location** | `package.json` (deps `multer`, `zod`, `winston`, e possivelmente outras transitivas); `SECURITY.md:155-165` declara pinados sem caret. |
| **Evidence** | SECURITY.md declara como **pinadas sem caret**: `bcrypt`, `express`, `express-rate-limit`, `helmet`, `jsonwebtoken`, `multer`, `pg`, `winston`, `zod`. Na prática, `package.json` reter `^` em pelo menos `multer`, `zod`, `winston` (e provavelmente outros a confirmar via `npm ls`). `npm ci` mitiga em prod, mas o descompasso é fonte de surpresas em PRs de upgrade e falsos positivos em gate de segurança. |
| **Impact** | Política declarada ≠ política aplicada. Em PR de upgrade dev, `npm install` pode trazer minor com breaking-change ou CVE novo (gate atual é `npm audit --audit-level=moderate`, mas caret permite minor sem PR de upgrade; patch pode pular a janela de gate). |
| **Fix recomendado** | (a) Alinhar `package.json` removendo `^` dos pacotes listados no SECURITY.md. (b) Substituir a lista nominal por uma chamada programática (`security-check.mjs`) que consulta `npm ls <pkg> --json=depth=0` e gera o relatório de pinning. |
| **Mitigation** | `npm ci` em prod (já praticado). Gate gradual: bump manual com PR dedicado. |
| **Sub-spec destino** | **3** (decisão: remover caret OU reescrever SECURITY.md para refletir a realidade). |

### L-01 — Cross-site forced logout (CSRF skip em POST /auth/logout)

| Campo | Valor |
|---|---|
| **Rule ID** | A05:2025 (Security Misconfiguration) + OWASP CSRF Cheat Sheet |
| **Severity** | **Low** (Risk = Low × Medium — nuisance, não privilege escalation) |
| **Location** | `src/expressApp.ts:173-176` (skip CSRF para `/auth/*`) + `src/modules/auth/router.ts:51` (`POST /auth/logout`) |
| **Evidence** | O middleware CSRF é montado em `/api/v1` **exceto** `/auth/*`. O endpoint `POST /api/v1/auth/logout` (router:51) aceita cookie auth —第三方页面 pode forçar o usuário a fazer logout via auto-submitted form/IMG. O endpoint usa cookies + limpa-os como efeito. |
| **Impact** | Logout forçado é nuisance (derruba sessão ativa), não vazamento nem privilege escalation. Em apps sensíveis a disponibilidade, vetor para DoS individual persistente. |
| **Fix recomendado** | Decidir conscientemente: (a) aceitar o skip (logout nuisance-only), ou (b) incluir `/logout` no CSRF (admin/core de UX). Prática comum em produtos maduros = manter skip em `/auth/*` e aceitar L-01. |
| **Mitigation** | `cookies.lax` + `httponly` reduzem exposição; curto `max-age` do token (15min) reduz janela. |
| **Sub-spec destino** | **2 (suite)** — teste regressivo que confirma logout-via-CSRF é nuisance, não privilege escalation. **3 (correção)** só se análise de produto mudar a equação. |

### L-02 — Dead code (forgotPassword + saveResetToken)

| Campo | Valor |
|---|---|
| **Rule ID** | A06:2025 — footprint |
| **Severity** | **Low** (cosmético) |
| **Location** | `src/modules/auth/controller.ts:145-151` (controller retorna 501 fixo, não chama service); `src/modules/auth/service.ts:137-139` (lança 501); `src/modules/auth/repository.ts:75-80` (`saveResetToken` só reachable via `service.forgotPassword`, que é unreachable). |
| **Evidence** | O controller expõe `POST /api/v1/auth/forgot-password` mas hardcoda 501 — não chama service. Service lança 501 em `forgotPassword()`. `repository.saveResetToken()` é dead via service; só reachable se algum caminho novo for adicionado. `authRouter.post('/forgot-password', authController.forgotPassword)` está montado e taxa-limitado (5/15min), mas toda chamada retorna 501. |
| **Impact** | Footprint de código morto aumenta superfície de manutenção e dificulta auditoria futura. Não-impacta security real. |
| **Fix recomendado** | Ou (a) remover endpoint, controller, service, repository, e taxa-limit (pré-anunciado como "não implementado"); ou (b) implementar de fato (email + token + bcrypt). Requer decisão de produto. |
| **Mitigation** | Limite de taxa já impede abuse do placeholder. |
| **Sub-spec destino** | **3 (cosmético)** — remover ou implementar. Remoção é a escolha conservadora. |

## 5. Categorias Avaliadas sem Achado

- **Command Injection:** grep por `child_process`, `exec`, `spawn`, `eval` — ausente em server code.
- **Path Traversal:** `sendFile`/`download`/`fs.readFile` com `req.params` ou `req.query.path` — ausente.
- **Template Injection (SSTI):** nenhum template engine + nenhum `res.render` — n/a.
- **Insecure Deserialization:** sem `JSON.parse` em rotas de input user-controlled direto para execução; redacted via `JSON.parse(JSON.stringify(req.body))` no audit (clona, não executa).
- **Cookie tampering:** valores via `sameSite=lax` + assinatura HMAC do JWT.
- **Race conditions em payments/finance:** cash-deposit financial é corrigido por transações DB no Supabase (PostgreSQL) — fora do escopo deste scan.

## 8. Riscos & Restrições deste Relatório

- **Local-only scan:** análise estática via leitura de código. Validações dinâmicas (race, blocking, fuzz em inputs atípicos) **não foram executadas**. Achados marcados precisam de PoC em ambiente isolado para confirmação.
